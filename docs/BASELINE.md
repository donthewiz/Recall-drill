# Phase 0 Baseline — Trial-Count Simulation

Generated by `npm run simulate` (`test/simulate.report.ts`) against the
**current (pre-C1-C7) state machine**, as extracted into `drillEngine.ts` in
Phase 0. This is the scoreboard later phases (C1 forward-chaining, C2 lenient
grading, C5 cue fading) diff their own numbers against, per Part 4 of
[`docs/V2-HANDOFF.md`](./V2-HANDOFF.md).

- Config: `encodeReps: 3`, `chunkDifficulty: 35`.
- Fixture decks: `test/fixtures/shortDeck.ts` (12 term/definition cards, short
  backs) and `test/fixtures/proseDeck.ts` (12 prose cards, backs averaging
  ~18 words).
- Learner models: `perfect` (always correct), `realistic` (0.55 base on a
  blind attempt, +0.12 per prior exposure, capped 0.95), `struggling` (0.3
  base, +0.08 per exposure, capped 0.95). Copy-typing (attempt 0, target
  visible) is treated as always-correct for all three models — it's
  transcription, not retrieval.
- `wallClockEstimate = keystrokes / 4.5 cps + totalTrials * 1.5s` (both
  constants are tunables documented in `test/simulate.ts`, not pinned by the
  handoff doc).

## Notes

- `shortDeck`'s backs are all ≤3 words by design, so every card lands on the
  `full` stage (no chunking at all) — that's why its stage breakdown never
  shows `chunks`/`combine`/`remediate`. This isolates the encode-vs-cycle
  cost independent of the chunking ladder.
- `proseDeck`'s numbers move a lot between learner models specifically
  because of the *exhaustive* combine ladder (`buildCombineSequence` emits
  `n(n-1)/2` windows) compounding with B1's remediation misfires — this is
  exactly the cost C1 (forward chaining) and B1's fix (Phase 1) target.
- These numbers include realistic-learner and struggling-learner runs whose
  `Math.random()`-driven correctness draws are stochastic per run; re-running
  `npm run simulate` will produce slightly different (but similarly-scaled)
  numbers for `realistic`/`struggling` — `perfect` is deterministic and will
  always match exactly.
